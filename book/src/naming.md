# Ponko naming and compatibility

Ponko is the primary spelling in Rust, C, C++, tools and newly written files.
The migration is additive: C ABI **version 2**, layouts, enum values, ownership
and calling conventions are unchanged. See
[STABILITY.md](https://github.com/ponkoengine/ponko/blob/main/STABILITY.md).

## Native code

New C programs include `ponko.h` and use `Ponko*` types, `PONKO_*` constants
and real exported `ponko_*` functions. Dynamic loaders look up those same
`ponko_*` names. New C++ programs include `ponko.hpp` and use `ponko::`,
`PONKO_PROFILE_SCOPE` and `PONKO_COUNT_CPP_ALLOCATIONS`. Link `ponko_ffi`.
Neither primary header includes a legacy header or introduces legacy names.
`ponko.h` is generated by cbindgen from the primary Rust declarations; the
C++ wrapper is maintained in `ponko.hpp`.

The default `ponko_ffi` feature `legacy-names` additionally exports the old
`crabby_*` symbols as forwarding functions and exposes deprecated Rust
`Crabby*`, `crabby_*` and `CRABBY_*` aliases. Existing binaries and dynamic
loaders continue to resolve the original symbols. Deprecated `crabby.h` and
`crabby.hpp` are thin source shims over the primary headers; both generations
may be included in either order. The C shim maps struct/enum tags as well as
function names, so callbacks and function pointers use identical types.

A distribution exclusively for new clients can opt out of `legacy-names`
with `--no-default-features` and select the other features it needs explicitly.
That distribution deliberately cannot load existing binaries requiring the
old symbols. Normal builds keep compatibility enabled. Source users of the
legacy headers can still compile against the primary exports.

Regenerate the primary C header with:

```sh
cbindgen --config crates/ponko_ffi/cbindgen.toml crates/ponko_ffi > include/ponko.h
python3 scripts/generate-ponko-header.py
```

The second command generates the deprecated C shim and Rust forwarding layer
from primary declarations. `--check` rejects stale outputs. Native CI also
checks every dynamic export, mixed-header clients and the retained ABI-2
baseline header and layouts.

## Environment and build settings

Use `PONKO_*` runtime settings and the `PONKO_LIBRARY_DIR` / `PONKO_INCLUDE_DIR`
CMake cache variables. The matching `CRABBY_*` names are deprecated fallbacks.
**Presence of the Ponko spelling wins**, even if it is empty, invalid or `0`.
Fallback occurs only when it is absent. The engine and MCP server warn once
per process when a deprecated environment fallback is selected; CMake warns
when a deprecated cache fallback is selected.

MCP launch sets both spellings to support older executables. Explicit launch
overrides follow the same precedence. `Color::PONKO_DARK` replaces the
deprecated Rust alias `Color::CRABBY_DARK`.

## Persistent and external identifiers

New output uses the Ponko spelling; readers retain the old spelling:

| Surface | Primary output | Deprecated input |
|---|---|---|
| World saves (version 1) | `ponko-world` | `crabby-world` |
| Prefabs (version 1) | `ponko-prefab` | `crabby-prefab` |
| glTF in-between frames | `ponkoMorphFrames` | `crabbyMorphFrames` |
| glTF animated morph targets | `ponkoAnimatedTargets` | `crabbyAnimatedTargets` |
| Instance registry on Unix | `~/.ponko/instances` | `~/.crabby/instances` |
| Instance registry on Windows | `%LOCALAPPDATA%\ponko\instances` | `%LOCALAPPDATA%\crabby\instances` |
| Web embedding canvas | `ponko` | `crabby` |
| Reference benchmark JSON `engine` | `ponko` | Historical reports remain readable JSON |

MCP searches both default registries, even if the new directory exists or
has no entries; the primary entry wins for duplicate instance IDs. An explicit
`PONKO_INSTANCES_DIR`, its legacy fallback, or a custom `Config` directory
restricts discovery to that directory. New engines register only in the new
default directory. MCP launch logs also use the new home directory. Old MCP
servers do not automatically discover the new default: set an explicit shared
instance directory when using an old server with a new engine.

For glTF extras and embedded canvases, the primary spelling wins when both
exist. New saves and importer output require a new reader; older engines do
not recognize the new format tags. Existing old saves and prefabs load without
changing their schema version. Keep old source files if an older engine still
needs to read them.

MCP tool names, parameters, control methods and the negotiated MCP protocol
versions already use neutral or Ponko names and remain unchanged. Steam
message-lobby metadata uses `ponko_protocol=ponko-messages-1`, accepts the
legacy version-1 spelling, and publishes a deprecated legacy metadata entry
for old peers. Unknown primary versions are rejected rather than falling back.
The packet encoding and version are unchanged.

## Deprecation and removal schedule

Legacy names are deprecated on **2026-11-10**. They remain supported for at
least one minor release and until **2027-11-10**. Removal can occur only in a
future major release on or after that date, with a changelog migration notice;
the date does not automatically disable anything. This schedule covers native
symbols and shims, Rust aliases, environment/cache fallbacks, legacy persisted
identifiers, registry discovery, canvas fallback and protocol metadata aliases.
No removal is part of this change, and ABI version 3 is not introduced.

## Inventory

`naming-inventory.json` inventories the remaining deprecated compatibility
code/coverage and migration instructions, historical release notes and legal
notices. Existing README files and historical baseline fixtures are preserved.
`scripts/check-naming.py` rejects new legacy-bearing files and increases beyond
the reviewed per-file budget. Review intentional compatibility-layer changes
before refreshing the inventory with `--inventory`; do not weaken the check.
