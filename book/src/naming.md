# Ponko naming and compatibility

Ponko is the primary spelling in Rust, C, C++, tools and newly written files.
The migration is additive: C ABI **version 2**, layouts, enum values, ownership
and calling conventions are unchanged. See
[STABILITY.md](https://github.com/ponkoengine/ponko/blob/main/STABILITY.md).

## Native code

New C programs include `ponko.h` and use `Ponko*` types, `PONKO_*` constants
and real exported `ponko_*` functions. Dynamic loaders look up those same
`ponko_*` names. New C++ programs include `ponko.hpp` and use `ponko::`,
`PONKO_PROFILE_SCOPE` and `PONKO_COUNT_CPP_ALLOCATIONS`. Link `ponko_ffi`.
Neither primary header includes a legacy header or introduces legacy names.
`ponko.h` is generated by cbindgen from the primary Rust declarations; the
C++ wrapper is maintained in `ponko.hpp`.

The default `ponko_ffi` feature `legacy-names` additionally exports the old
`crabby_*` symbols as forwarding functions and exposes deprecated Rust
`Crabby*`, `crabby_*` and `CRABBY_*` compatibility names. Enum-free types are
aliases. Legacy enums and their containing value structs are generated as
layout-equivalent types, preserving explicit and wildcard variant imports;
forwarders convert values and compile-time assertions check sizes, alignments,
field offsets and discriminants. Existing binaries and dynamic
loaders continue to resolve the original symbols. Deprecated `crabby.h` and
`crabby.hpp` are thin source shims over the primary headers; both generations
may be included in either order. The C shim maps struct/enum tags as well as
function names, so callbacks and function pointers use identical types.

A distribution exclusively for new clients can opt out of `legacy-names`
with `--no-default-features` and select the other features it needs explicitly.
That distribution deliberately cannot load existing binaries requiring the
old symbols. Normal builds keep compatibility enabled. Source users of the
legacy headers can still compile against the primary exports.

Regenerate the primary C header with:

```sh
cbindgen --config crates/ponko_ffi/cbindgen.toml crates/ponko_ffi > include/ponko.h
python3 scripts/generate-ponko-header.py
```

The second command generates the deprecated C shim and Rust forwarding layer
from primary declarations. `--check` rejects stale outputs. Native CI also
checks every dynamic export, mixed-header clients and the retained ABI-2
baseline header and layouts.

## Environment and build settings

Use `PONKO_*` runtime settings and the `PONKO_LIBRARY_DIR` / `PONKO_INCLUDE_DIR`
CMake cache variables. The matching `CRABBY_*` names are deprecated fallbacks.
**Presence of the Ponko spelling wins**, even if it is empty, invalid or `0`.
Fallback occurs only when it is absent. The engine and MCP server warn once
per process when a deprecated environment fallback is selected; CMake warns
when a deprecated cache fallback is selected.

MCP launch sets both spellings to support older executables. Explicit launch
overrides follow the same precedence. `Color::PONKO_DARK` replaces the
deprecated Rust alias `Color::CRABBY_DARK`.

## Persistent and external identifiers

New output uses the Ponko spelling; readers retain the old spelling:

| Surface | Primary output | Deprecated input |
|---|---|---|
| World saves (version 1) | `ponko-world` | `crabby-world` |
| Prefabs (version 1) | `ponko-prefab` | `crabby-prefab` |
| glTF in-between frames | `ponkoMorphFrames` | `crabbyMorphFrames` |
| glTF animated morph targets | `ponkoAnimatedTargets` | `crabbyAnimatedTargets` |
| Instance registry on Unix | `~/.ponko/instances` | `~/.crabby/instances` |
| Instance registry on Windows | `%LOCALAPPDATA%\ponko\instances` | `%LOCALAPPDATA%\crabby\instances` |
| Web embedding canvas | `ponko` | `crabby` |
| Reference benchmark JSON `engine` | `ponko` | Historical reports remain readable JSON |

MCP searches both default registries, even if the new directory exists or
has no entries; the primary entry wins for duplicate instance IDs. An explicit
`PONKO_INSTANCES_DIR` or its legacy fallback restricts discovery to that
directory. A custom `Config` path different from the default also stays
isolated. Configuring the default path opts into compatibility discovery; set
an explicit environment override (even to the default path) to restrict it. New engines register only in the new
default directory. MCP launch logs also use the new home directory. Old MCP
servers do not automatically discover the new default: set an explicit shared
instance directory when using an old server with a new engine.

For glTF extras and embedded canvases, the primary spelling wins when both
exist. New saves and importer output require a new reader; older engines do
not recognize the new format tags. Existing old saves and prefabs load without
changing their schema version. Keep old source files if an older engine still
needs to read them.

MCP tool names, parameters, control methods and the negotiated MCP protocol
versions already use neutral or Ponko names and remain unchanged. Steam
message-lobby metadata uses `ponko_protocol=ponko-messages-1`, accepts the
legacy version-1 spelling, and publishes a deprecated legacy metadata entry
for old peers. Unknown primary versions are rejected rather than falling back.
The packet encoding and version are unchanged.

## Deprecation and removal schedule

Legacy names are deprecated on **2026-11-10**. They remain supported for at
least one minor release and until **2027-11-10**. Removal can occur only in a
future major release on or after that date, with a changelog migration notice;
the date does not automatically disable anything. This schedule covers native
symbols and shims, Rust aliases, environment/cache fallbacks, legacy persisted
identifiers, registry discovery, canvas fallback and protocol metadata aliases.
No removal is part of this change, and ABI version 3 is not introduced.

## Inventory

`naming-inventory.json` inventories the remaining deprecated compatibility
code/coverage and migration instructions, historical release notes and legal
notices. Existing README files and historical baseline fixtures are preserved.
`scripts/check-naming.py` rejects new legacy-bearing files and increases beyond
the reviewed per-file budget. Review intentional compatibility-layer changes
before refreshing the inventory with `--inventory`; do not weaken the check.

## Dimension modules

Start with `use ponko::prelude::*;`, then `use ponko::d2::*;` or
`use ponko::d3::*;`. Both expose `Transform`, `Camera`, `RigidBody`, `Collider`,
`Velocity`, `Shape`, `Physics`, and `Hit` (physics features required).
`d2` also holds `Sprite`, `TileMap`, `Attached`, `SpriteSheet`, `Animation`
and the 2D grids (`SpatialGrid`, `NavGrid`, `FlowField`); `d3` holds models,
materials, lights, decals, text, particles, terrain, animation, audio sources
and navigation agents. A game with both dimensions in one file imports one
module and qualifies the other (`d2::Transform` next to bare 3D names).
The modules are aliases for existing types: layout, component identity and saved
names are unchanged. Context fields remain `camera`/`camera3d` and
`physics`/`physics3d` so both dimensions can coexist; their types are
`d2::Camera`/`d3::Camera` and `d2::Physics`/`d3::Physics`.

The prelude keeps `Transform2D`, `Camera2D`, `Transform3D` and `Camera3D` for
code that uses both dimensions; in code for one dimension, prefer the module
names (`d2::Transform`, `d3::Camera`). The other old root spellings were
removed (see [below](#the-root-glob)):

Use `physics.cast_ray_filtered(origin, direction, max_distance, filter)` in
both dimensions and `physics.overlap_ball(center, radius, filter, &mut hits)`
for circles/spheres. Filters default to solid colliders, can include sensors,
and can exclude an entity. Both `Hit` types carry `entity`, `point`, `normal`
and `distance`; vectors have the matching dimension. `apply_impulse` and `mass`
share the same convention. Existing `cast_ray`, `entities_at`,
`entities_in_circle` and `overlap_sphere` calls retain their behavior.
The issue sketch called the common method `cast_ray`; Rust cannot overload
inherent methods by argument count, so the additive filtered spelling preserves
the existing three-argument 2D call and four-argument 3D call.

`Ctx::spawn_prefab(path, placement)` also accepts a `Vec3` or `d3::Transform`.
A 3D transform supplies position, rotation and scale; a 2D position keeps the
prefab's existing rotation and scale. Saved component names remain unchanged.

## Prelude and service imports

`use ponko::prelude::*;` is the default game import. It includes the game loop,
context, ECS, math, input, colors, textures/sounds/fonts, common transforms and
reflection registration. Add `d2::*` or `d3::*` for one dimension, then explicit
service imports as needed. `Pose`, `Material` and `Job` are deliberately absent
from the prelude so games can define them freely.

| Area | Canonical module |
|---|---|
| Networking, replication, interest, Steam | `net` (`net::steam` is the SDK) |
| Frame/per-system reports, budgets, scopes | `perf` |
| Materials, effects, compute, targets, quality | `render` |
| Clips, graphs, skeletal animation, IK | `anim` |
| Heightfields, terrain tiles, terrain streaming | `terrain` |
| Retained UI and layout | `ui`, `ui::layout` |
| Physics and navigation | `physics`, `physics3d`, `nav`, `d2`, `d3` |
| Reflection JSON | `reflect::json` |
| Advanced ECS and native storage | `ecs_core` |

### The root glob

The crate root holds the modules and exactly what the prelude holds, as the
same items, so `use ponko::*;` brings in the prelude and the modules, and is
never ambiguous next to `use ponko::prelude::*;`. Everything else is reached
through its module. Compatibility exports of the prelude items are hidden
from the root rustdoc page; module docs are the discovery path.

The old root spellings of moved items are gone. The move first kept them as
`#[deprecated]` re-exports, but rustc does not warn through a re-export, so
old code got no hint to move; the changelog lists every removed name with
its replacement. Moving off them:

- A type, trait or function: import it from the module the changelog names
  (`ponko::RigidBody3D` is `ponko::d3::RigidBody`, `ponko::Net` is
  `ponko::net::Net`). Canonical modules export the original types, so
  identity, layouts, saves and flat C/C++ names do not change.
- A built-in system (`step_physics`, `draw_sprites`, ...): `ponko::systems`.
- A root constant that became an associated constant: `d3::Decal::MAX` and
  `MAX_PER_CLUSTER`, `spatial::SpatialGrid::<()>::SORT_EVERY`,
  `render::GraphicsQuality::MIN_RENDER_SCALE` and `MAX_RENDER_SCALE`,
  `terrain::TerrainTile::LODS` and `LAYERS`, `d3::PointLight::SHADOW_SIZE`,
  `SHADOW_ATLAS_SIZE` and `MAX_SHADOW_VIEWS`, and
  `render::GlobalIllumination::MAX_PROBES` and `MAX_PROBES_PER_FRAME`.
  Constants that belong to one module keep their name there
  (`net::MAX_PLAYERS`, `input::MAX_GAMEPADS`, `random::DEFAULT_SEED`,
  `physics3d::PHYSICS3D_HZ`, `scenario::SCENARIO_VERSION`,
  `streaming::DEFAULT_UPLOAD_BUDGET`).
- Crates and helpers: `serde_json` is `reflect::json` (and `Value` is
  `reflect::json::Value`; `json!` stays in the prelude), `steamworks` is
  `net::steam`, `ui_layout` is `ui::layout`, `QueryFilter` and `ViewQuery`
  (the ECS ones) are in `ecs_core`, `Interpolate` is `net::Interpolate`,
  `FieldType` and `ValueSchema` are in `reflect`, `RawFlowView` is
  `flow::RawFlowView`, `RawGridView` is `spatial::RawGridView`.

`Instant` is `perf::Instant`. `Animation` (the sprite-sheet animation) is in
`d2`, not the prelude: games often name their own type `Animation`.

### Root modules and crates of the same name

`use ponko::*;` also brings in the root modules (`audio`, `input`, `net`,
`render`, `ui`, `random`, `events`, ...), which are new in this release. With
the root glob and a dependency of the same name, a path in code
(`net::connect()`) means `ponko::net`, and a `use net::...;` declaration is
an error (E0659: `net` is ambiguous). Write `::net::...` (`use ::net::connect;`)
for the crate, or use `use ponko::prelude::*;`, which holds no such modules
apart from `d2`, `d3`, `systems` and `actions`. The clock module is private,
so the `time` crate is not shadowed; `Instant` is `perf::Instant`.

`ponko::nav` names the navigation-mesh types as `d3` does (`NavMesh`,
`NavAgent`, `NavObstacle`), so they don't clash with the root's `Mesh`.

The engine's built-in systems (`step_physics3d`, `draw_sprites`,
`animate_sprites`, `rebuild_spatial_grid`, ...) live in `ponko::systems`, and
each has a `Systems` id for `Game::remove` ([Systems](systems.md)).

Use `world.raw()` for dynamic components and resources (`get_dynamic`,
`insert_dynamic`, `spawn_dynamic`, `remove_dynamic`, the `*_resource_dynamic`
calls), chunks (`for_each_chunk`) and archetypes; `world.raw_ref()` supplies
read-only dynamic inspection. These views borrow the same world and preserve
every pointer/layout requirement of the existing native interface. The same
methods on `World` itself were removed with the old root spellings. The C
bindings call the same functions through `raw()`.

### Native filtered queries and prefab placement

The native headers keep flat names. C uses `PonkoQueryFilter2D` (zero means
solids only), `ponko_ctx_cast_ray_filtered`, and `ponko_ctx_overlap_ball`.
Existing 3D ray/sphere calls already accept `PonkoQueryFilter3D`.
C++ offers `filter2d`/`filter3d` and overloads of `cast_ray_filtered` and
`overlap_ball` with the same argument order in both dimensions. The filter is
explicit, so the vector/filter types select the dimension. Existing ray and
overlap methods retain their behavior.

C prefab placement adds `ponko_ctx_spawn_prefab3d` (position, preserving saved
rotation/scale), `ponko_ctx_spawn_prefab_transform3d` and
`ponko_ctx_spawn_prefab_transform2d` (complete transform). C++ uses the same
flat method names without the `ponko_ctx_` prefix. These are separate names
rather than overloads of the old `spawn_prefab`: otherwise an existing
`spawn_prefab(path, {x, y})` would become ambiguous with a 3D aggregate.
Outputs are validated before spawning; invalid paths and null outputs do not
spawn an entity. The compiled native `dimensions.c` and `dimensions.cpp` tests
exercise filtering, buffer sizing, errors, placement and legacy calls.
